# Report schema

## Transient full-source binding

`SourceBrowseDocument` is a strict transient UI response, not a persisted analysis section. Authenticated `GET /api/code-browser/document` accepts the saved report SHA-256, nonnegative selection revision and an exact path or entity identity, plus existing saved-run selectors. It rejects roots, arbitrary paths and preview/search/paging options. The result echoes the bound report and revision and contains a `SourceDocument` with verified original UTF-8 text, original-byte hash/count, line count, newline style, final-newline state and editability. Reads require an explicit server `--source-root` and stay within 1 MiB/20,000 lines; mixed or bare-CR newlines remain read-only. Disabled, unavailable, mismatched, oversized and invalid-encoding results disclose no source or text metadata. Responses use `Cache-Control: no-store`; source text never enters analytical JSON, browsing indexes or workspace generations. No draft, save or execution route is implied.

Source hashes bind physical file bytes, including newline sequences. Python's AST inputs are decoded without universal-newline normalization; clone text normalization remains a separate analytical operation. This makes CRLF and LF distinct source bindings even when AST structure is unchanged. Source-unreadable interface contributions produce `interface-source-read-error` with partial section/provider state rather than a crash or successful empty result.

## Static invocation evidence

`static_call_occurrences` retains distinct syntactic invocation sites; `static_call_coverage` accounts for each collected source with observed, retained and omitted counts and an explicit completeness state. The `static-call-occurrences` section is separate from function-commonality, lexical callee names and runtime profiles. Focused contract/dictionary commands leave collection disabled. `max-static-call-occurrences` is a strict configuration bound (default 100,000; range 1–1,000,000) participating in analytical identity.

Each occurrence binds its source-file identity, language, module, exact source-hashed invocation evidence, normalized syntactic scope, evaluation context and independent conditional/deferred/unknown flags. `callee_spelling` and `enclosing_subject_id` are nullable: spelling is not dispatch resolution, and an enclosing subject is only a navigation anchor. Recognized Ruby operator methods retain their invocation sites with null spelling and an explicit operator-spelling limitation; their names are not serialized as identifier chains. This does not relax validation of unrelated malformed provider records. Content-derived occurrence identities include the normalized observation and a portable parser/configuration/normalization identity. Repeated invocations remain distinct. No source text is persisted by these records.

The saved-only `static-call-sites` table preserves unknown callee/anchor values as explicit null scalars. `static-call-graph` connects source-file nodes to invocation nodes using `source-contains-call-site` edges; it is neither a caller-to-callee graph nor an execution-order graph. The existing `lexical-call-graph` and runtime graphs remain separate. `query --call-site ID` returns invocation evidence and its recorded navigation relationships without reading source. Collection and UI qualification status is tracked in the [current scope and roadmap](roadmap.md).

Saved comparisons include `static-call-occurrence` records keyed by content-derived occurrence IDs and `static-call-coverage` records keyed by `static-call-coverage:SOURCE_FILE_ID`. A changed occurrence is removed/added when its observation identity changes; per-source coverage changes remain one changed record. Occurrence source choices use recorded evidence only; coverage rows are explicitly spanless. Parser/normalization/configuration/Python provenance remains part of observation identity rather than being erased for cross-environment equality.

## Finding suppression annotations

An optional `finding_suppression_evaluation` stores an explicit `evaluated_on` date and sorted, exact-ID acceptance rules. Each matched finding carries a typed `suppression` record with its finding ID, rationale, `expires_on`, `evaluated_on` and `accepted` or `expired` status. Expiry takes effect on the declared expiry date (`evaluated_on >= expires_on`). Absence of an annotation means not suppressed. Strict validation rejects mismatched finding IDs, absent/conflicting evaluation policies and contradictory expiry states. Unmatched rules remain in the policy so their scope is inspectable without fabricating findings.

Evaluation never uses the report viewer's clock. Acceptance does not remove findings or evidence, alter severity, change summary counts/completeness, qualify proposals, or change `--fail-on-findings`. Configuration and run identities bind the policy/date. This is distinct from candidate-decision worklist hiding. Presentation integration and qualification are tracked in the [current scope and roadmap](roadmap.md).

Dates must be quoted TOML strings. Configure both the explicit evaluation date and one or more unique rules sorted by finding ID:

```toml
[tool.code-analysis]
suppression-evaluation-date = "2026-09-22"

[[tool.code-analysis.accepted-suppressions]]
finding-id = "COPY-EXACT-FINDING-ID-FROM-REPORT"
rationale = "Reviewed and intentionally retained for this release."
expires-on = "2026-10-01"
```

Rules match the full finding ID literally; no wildcard, module-wide or rule-wide matching is performed. Changing the evaluation date requires a new analytical result; merely opening saved JSON does not renew or expire acceptance.

Persisted evidence now uses required top-level `source_bindings` and `evidence_catalog` arrays. A source binding contains `binding_id`, `logical_path`, `language`, and `source_sha256`. Old draft layouts without bindings are rejected; there is no alternate loader.

Source locations remain directly accessible with `jq`, without a source checkout or parser:

```sh
jq '(.source_bindings | INDEX(.binding_id)) as $sources | .evidence_catalog[] | . as $e | $sources[$e.binding_id] as $s | {evidence_id, path: $s.logical_path, language: $s.language, source_sha256: $s.source_sha256, start_line, start_column, end_line, end_column, provider, observation, confidence}' report.json
```

Commonality admission also requires `index_dimension_rejections` and `index_dimension_rejections_exact`. These describe distinct non-clone pairs excluded before candidate materialization because they cannot share the configured minimum number of ownership dimensions. They are separate from `unique_candidates` and its admission/rejection arithmetic. A completed index gives an exact count; early termination gives a counted prefix with false certainty and positive candidate-bound omissions. Bounded rejection examples do not imply that all excluded pairs were materialized. Structural clones bypass this preselection; retained candidates still undergo bilateral coverage checks. No thresholds are relaxed.

Python function profiles exclude unshadowed builtin names and locally bound handler/import/declaration/pattern names from bare attributes/globals ownership features. Call resolution follows explicit function scopes through their enclosing functions to the module, skipping class namespaces for bare method-body names. Unambiguous direct helper declarations and captured helpers retain their qualified identities, including recursion. Parameters, reassignment, repeated declarations and other unproven binders prevent resolution through a same-spelled outer function or module import. Bare calls do not resolve to unrelated class methods or inaccessible closures. Local import aliases, conditional definitions and global/nonlocal rebinding remain conservative unresolved cases at this feature boundary. Signatures remain descriptive, explicit global/nonlocal references remain observable, and possible shadowing or capture is handled conservatively. This is static syntax evidence, not proof of runtime namespace state or common ownership. A builtin spelling or shadowed callee cannot supply a second ownership dimension for pair admission; structural clone evidence remains separately eligible.

Commonality admission records require `candidate_bound_omissions_exact` alongside the nonnegative `candidate_bound_omissions`. When generation stops at the bound, the count is a positive known lower bound, the flag is false, and the unvisited total is unknown. Exact zero is true only when candidate generation finishes. Python and JavaScript contributions preserve inexactness when merged. Positive omissions require explicitly incomplete commonality section coverage with a truncation count. The admission table labels each count as exact or lower-bound; the signal-quality policy and provider diagnostic disclose the unknown tail. Counting that tail must not introduce unbounded work. This updates the single unreleased schema in place; older draft artifacts lacking the required certainty field are rejected rather than guessed or migrated.

This storage normalization changes canonical report-byte hashes, not analytical entity/evidence IDs or configuration/run identities. Existing JSON remains readable when it satisfies the current strict model, but receipts/caches/captures bound to previous canonical bytes must not be silently rewritten or promoted. Rebuild a derived index from the saved JSON when necessary; current report/profile binding checks remain authoritative. This does not introduce a compatibility loader or alter standalone profile serialization.

Executable paths, Node installations, package caches, native wheel locations, and temporary parser paths remain local provenance. Observation, fingerprint, projection, and cache identities bind the relevant source hash and analyzer/parser configuration.

Completeness is `complete`, `partial`, or `failed`. A syntax/read error or finding truncation makes the native scan partial. Provider states distinguish `success`, `partial`, `unavailable`, `timeout`, `nonzero`, `malformed`, and `failed`.

A Python-only scan records the JavaScript front end as disabled or not requested and does not require a JavaScript dependency. When JavaScript is selected or discovered in scope, parser absence, syntax failure, unsupported syntax, truncation, or malformed output constrains the corresponding section and overall completeness; none can be represented by an empty successful section. Language, logical source, span, evidence, and source-hash references must agree across every section.

The authoritative report contains every R1 section plus a deterministic run identity, stable analysis subjects, Phase 2 contracts/dictionary/flow/topology evidence, and Phase 3 clone fragments/clusters, function profiles/commonalities, state resources, side effects, responsibility clusters, architecture estimates/contracts, and refactoring proposals. Stable record identities are typed by prefix, unique, and sorted. Report validation rejects every dangling or duplicate relationship, including Phase 3 cluster, estimate, finding, and proposal references. Disabled analyzer sections carry no observations and cannot masquerade as successful empty evidence. Partial or failed required sections constrain overall completeness.

Dictionary analysis does not expose mutable mapping bags as a public or internal module boundary. Raw operations and shape-join values use frozen slotted dataclasses; persisted subjects, shapes, variants, fields, lifecycle states, discriminators, defaults, dictionary observations, flows, projections, and report sections are strict frozen Pydantic v2 models. A shape contains one or more explicit variants rather than a flattened union of keys. Variants retain their discriminators and lifecycle-state references, while each field retains every separately evidenced requiredness observation instead of reducing always, optional, conditional, and unknown states to one value. Producer-provided defaults and consumer fallback defaults are separate collections. Each default is tagged as absent, explicit null, JSON literal, factory, expression, or unresolved. Dictionary observations distinguish literal-string, literal-non-string, dynamic, and unresolved keys; literal/factory/comprehension, read/write/delete, get/update/pop/setdefault/merge, membership, truthiness, coercion, iteration, unpacking, argument/return, and validation operations; and mutations before or after validation. Resolved flows become referentially validated edges; unresolved and ambiguous calls become explicit unresolved records and constrain completeness. Identities and reference lists are unique and deterministically ordered, evidence is required, and extra fields or coercive booleans are rejected.

Structure ownership distinguishes lexical local, module, class-body, and evidenced instance-receiver scopes. Class-body owners use a stable `<class>.NAME` logical component, while dataclass/direct receiver owners use `self.NAME`; classmethod access joins only through an exact receiver or lexical class name. The `concurrency` tuple retains exact recognized guard identities and outer-to-inner lexical nesting order as descriptive strings. It does not represent runtime lock success, complete coverage, or deadlock conclusions.

Structural validation rules also retain exact JSON-literal equality and membership relations for proven dictionary fields. These observations support schema-version and enum/state review while dynamic comparison values and runtime acceptance behavior remain unresolved.

Contracts contain one or more evidenced boundary occurrences rather than one flattened boundary enum. Each occurrence records its stable identity, boundary class, producer/consumer/definition direction, site subject, evidence, confidence, and limitations. Exact constructor/validation calls and function annotations create separate boundary subjects. Same-module and test-only classifications are syntax-exact; configured portable rules may resolve persisted, API/HTTP, or cross-subsystem use sites. An unmatched or conflicting cross-module classification is `unclassified-internal`, increments unresolved contract coverage, makes the report partial, and carries a limitation. `Finding` records affected subjects, contracts, shapes, and structures; supporting and counter-evidence; confidence; completeness; limitations; and likely validation needs. A Phase 2 finding requires an affected identity, validation needs, and either counter-evidence or a limitation. Heuristic evidence cannot produce an error finding. These records remain review evidence and never authorize refactoring.

The report loader validates directly against the authoritative model, rejects unsupported schema identifiers and unknown fields, and never rewrites a report during loading or summary rendering. Because the software is unreleased, there is no legacy report loader or migration path.

`validation_patterns` contains typed structural or operational classifications, stable referenced subject IDs, portable field identities, exact evidence sites, divergence and fail-open states, and limitations. Dictionary observations retain exact present, absent, truthy, and falsy predicates. Structural dictionary validation requires ownership proven by syntax; presence and key-value truthiness remain distinct, direct positive/negative static value-type checks and equal/not-equal literal exact-key-set checks retain their semantics, and presence/truthiness divergence requires both forms on the same evidenced field identity. An explicitly negative literal-field or exact-key-set condition whose branch contains only `pass` or provenance-resolved standard-library logging is retained as a syntax-only fail-open candidate with an outcome limitation. Dynamic-key membership, whole-mapping truthiness, error accumulation, fallback mutation, and arbitrary callbacks are excluded, and the flag is not proof that invalid runtime data is accepted. A separate bounded operational pass retains exact path-typed and resolved `os.path` checks used in conditions or direct boolean returns. It rejects arbitrary method-name matches and does not turn filesystem, path, symlink, metadata, or permission checks into structural findings. Dynamic type/key expressions, operational outcomes, and broader authorization/security/runtime checks remain unresolved.

The validated JSON report is the durable analytical record. Workspace `report.json` is canonical compact JSON; `--json` is an explicit pretty view and `--json-compact` emits the same canonical representation. Whitespace in an input report cannot affect its canonical identity. TSV, DOT, Mermaid, Markdown, SVG, PNG, and interface views must be reproducible from retained JSON without rescanning the target. Persisted projection JSON binds the canonical source report SHA-256, report and projection schema versions, filters, stable ordering, truncation, completeness, and limitations. Graph node/edge JSON is authoritative over its DOT or Mermaid rendering; TSV exports flatten only declared scalar columns. Git repository identity records whether churn and coupling used the default Python-only path scope or an explicitly configured repository-wide scope; projections do not silently widen that scope.

## Projection schema

Comparison summary tables may carry exactly two ordered input roles, `baseline` and `candidate`, each with its saved report identity. Other ordinary tables retain the single `source` plus optional decision-ledger contract; lone baseline, mixed source/comparison and duplicate input roles are rejected. Comparison-page exports bind both report hashes, applied change/kind/search filters, offset and limit to their projection identity. They distinguish filtered-out records from analytical omissions and records outside the exported page, preserving partial or failed source completeness. This table view does not replace the full comparison projection or authoritative report evidence.

`structure-lifecycle-graph` and `conversion-graph` use the existing strict `GraphProjection`; no analysis-report fields are added. Lifecycle nodes reference saved structure/subject/shape/state identities, and role/state-association edges retain evidence IDs. Conversion edge identities are the original `FlowEdge.flow_id`, preserving separate sites with the same endpoints and their resolution/confidence. Common projection identity, selection and omission counts apply. Role directions and observed-state links do not assert temporal transitions; shared owner does not assert representation identity.

`code-analysis-projection` version `1.0.0` is the strict persisted boundary for report-only views. Its discriminated Pydantic union covers table, graph, hierarchy, sequence, state, comparison, and review-packet projections. Projection inputs bind source-report schema identity and SHA-256; comparisons require distinct baseline and candidate roles. Selection limits, completeness, record counts, truncation, and limitations are explicit.

Projection rows, nodes, edges, clusters, hierarchy relationships, participants, events, states, transitions, comparison records, and review items have declared models rather than arbitrary payload dictionaries. Scalar table and metric values use an explicit tagged type that rejects bool-as-int and prevents nested dictionaries from leaking into TSV boundaries. Validators enforce unique identities, deterministic ordering, known graph endpoints, acyclic hierarchies, contiguous sequence positions, exactly one initial state, matching record counts, and required comparison inputs.

`reports/projection_json.py` serializes projection JSON with UTF-8, sorted object keys, stable record order, deterministic indentation or compact separators, and one trailing newline. Its loader rejects unsupported schema versions, unknown projection kinds, extra fields, malformed identities, and contradictory relationships.

Implemented builders include `signal-quality`, `commonality-admission`, `prevalent-features`, `proposal-admission`, `proposal-decisions`, `proposal-gates`, `refactor-shortlist`, and `subject-findings` alongside the Phase 3 clone, commonality, state, architecture, and refactoring views. `ProposalAdmissionFunnel` reconciles considered candidates, admitted candidates, call-resolution-only rejections, proposal-bound omissions, and retained proposals; up to 25 deterministic typed rejection examples do not change completeness because aggregate counts remain authoritative. `subject-findings` groups severity, category, rule, evidence, and proposal counts by strict subject identity after applying typed module/category/severity/rule filters; findings without a subject remain in the flat findings view and the active filtered count is disclosed as omitted. Function commonality is a sparse `MatrixProjection`: cells retain per-dimension intersections, left/right totals, and evidence identities rather than an opaque aggregate score. Selection records carry every filter plus independent table, node, and edge bounds and optional module/package collapse. Bounded graphs retain original, retained, and omitted counts and remain usable partial evidence; their command status is host `ENODATA`. JSON remains authoritative and every projection is reproducible without source access.

Phase 4J projections reuse these envelopes and add language-aware cross-module duplicate pairs, clone membership, normalized structural differences, differing branches/calls/constants/exceptions/state/effects, ownership and caller/test views, typed divergence reasons, suggested-owner evidence, and bounded refactor packets. They persist component evidence and explicit differences, never an opaque similarity or risk score. The projection registry and every retained projection operate without a parser, Node/npm, source tree, or rescan.

`ComparisonProjection.identical` is strict and must agree with its two canonical report SHA-256 identities. An identical comparison has zero records and cannot be truncated. Its equality result is explicit, while failed or partial input evidence retains that completeness and host errno status.

Report sections distinguish disabled, complete, partial, failed, truncated, and unavailable states. Bounds are explicit; crossing an analytical bound adds a diagnostic, makes coverage partial, and maps to host `ENODATA`. Commonality persists only admitted pairs plus a deterministic funnel covering postings, prevalence exclusions, unique candidates, bounded omissions, rejection classes, clone admissions, and final admissions. Candidate generation uses ownership-bearing dimensions, bilateral coverage, feature-prevalence suppression, and inverted indexes; names, docstrings, signatures, and control-flow shape cannot originate a pair. Every refactoring proposal has an ordered decision for ownership, domain, contract, state, side-effect, graph, SCC, cycle, layer, test, coverage, and runtime gates plus a required primary reason. A blocked proposal must identify a failed or unresolved blocking gate. Missing Phase 4 evidence alone produces `reviewable-incomplete`, not a false static rejection.

Candidate classification is deliberately conservative. Resolved cross-symbol dictionary flow may support a `TypedDict` candidate; discriminated variants plus structural validation may support an inferred Pydantic candidate; otherwise fully bounded syntax may remain a local implementation dictionary. Unresolved outbound flow suppresses classification. Dataclass, protocol, and intentionally-untyped compatibility labels are not emitted without evidence establishing those meanings. Every label is review evidence, not a migration or refactoring instruction.

## Query schema

`code-analysis-query` version `1.0.0` is the current strict draft response contract for bounded queries over one validated saved report. It is not a released compatibility generation and has no migration loader. The response binds the canonical source-report SHA-256 and run identity, exact selector, limit, continuation identity, returned count, truncation, source completeness, and limitations. Typed items identify their relationship and retain bounded evidence, confidence, completeness, related report identities, and limitations. Item ordering and continuation are stable; missing selectors and invalid continuations fail rather than returning a successful empty response. Query JSON is authoritative, compact JSON and concise Markdown are views, and the query service has no target path or source-reader input.

The `ComparisonProjection` provides a compatible full-report evidence delta. Its two inputs are tagged baseline and candidate and bind both report hashes and run identities. Compatibility requires identical schema, target, and static configuration identities; command names may differ. Stable static, contract, shape, clone, proposal, test, coverage, Git, and generation records are classified added, removed, changed, or unchanged using canonical record SHA-256 values. Non-identical projections retain global `ComparisonChangeCounts`, an `includes_unchanged` policy, and the eligible displayed-record count. Changes-only is the default; hidden unchanged records are counted but cannot create truncation. Identical inputs keep counts absent because equality is established before record expansion. Display truncation and input incompleteness separately constrain projection completeness. The delta is evidence about report change, not an architecture estimate or refactoring instruction.

Exact `dict(mapping)`, `json.dumps(mapping)`, and `json.dump(mapping, ...)` calls with statically owned dictionary arguments become conversion or serialization flow edges and are referenced by the corresponding structure. External serializer subjects are explicit report subjects. Repeated exact sites may produce an informational conversion-churn finding, but static call counts do not establish runtime frequency or cost. A serialization call is not a persistence claim: `persistence_boundary_ids` remain empty unless an independently evidenced configured contract boundary is uniquely classified `persisted`. Conflicting configured classes emit a diagnostic and make dictionary and structure coverage partial rather than silently selecting a class.

An exact no-argument `.clear()` call on a statically owned mapping is retained as a `clear` mutation observation and an `exact mapping clear observed` structure-cleanup fact. Exact `del mapping[key]` and `mapping.pop(key)` sites retain the separate `exact mapping entry removal observed` fact. Calls to `clear` with positional or keyword arguments are not accepted as cleanup evidence. These facts prove only syntax-owned removal sites; execution, reachability, lifecycle intent, completeness of resource cleanup, and runtime effectiveness remain unmeasured.

## Local persisted schemas

Project workspaces use separate host-local contracts:

- `code-analysis-workspace` version `1.0.0` establishes ownership, normalized project identity, tool creation version, and cache layout. A directory without a matching marker is never claimed.
- `code-analysis-run` version `1.0.0` records physical target/workspace paths, invocation time and duration, actual interpreter path, non-executing provider path inventory, the local storage-configuration identity, cache statistics, and the portable report SHA-256.
- `code-analysis-generation` version `1.0.0` binds an immutable analysis, coverage, or profile generation to physical local paths, timestamp, command array, interpreter, portable identity, and validated artifact hashes/sizes.

`code-analysis-profile-report` version `1.0.0` is a separate portable schema for workload identity, repetitions, normalized frames, callers/callees, timing statistics, resource observations, provider states, completeness, and limitations. Local manifests retain raw `.prof` and streams; portable profile JSON uses structural path classes and hashes. `code-analysis-change-report` version `1.0.0` is a discriminated explicit evidence contract: `source = "git"` stores bounded privacy-preserving commit/path/coupling records, while `source = "generations"` stores retained-generation intervals and sparse coupling without rescanning source. Git change evidence is not embedded into ordinary scans.

The required Phase 4P expansion extends the unreleased profile contract directly. It adds strict collection identity for repository commit/dirty state/source fingerprint, Python/platform/dependencies, redacted subject command, ordered workload steps, external artifacts, profiler configuration, collection scope, and proven subject PID/start identity. Runtime records retain every frame class, recursion and primitive/total calls, self/cumulative/per-call timing, callers/callees, category matches and precedence, static correlations, unobserved static subjects, filter/omission counts, and completeness. Temporary paths, labels, and timestamps are local manifest data and do not enter semantic collection identity.

One runtime report directory contains authoritative summary, category, identity, diagnostic, complete-callgraph, and static-correlation JSON plus deterministic TSV/Markdown/DOT/SVG/PNG projections and a strict manifest of relative artifact paths, sizes, hashes, generation state, and limitations. A presentation bound never deletes nodes, edges, or oversized-component membership from authoritative JSON. Offline ingestion and managed execution use separate discriminated manifests. Profile comparison rejects incompatible source, workload, external-artifact, profiler, PID, or collection-scope identities; an explicit diagnostic override remains ineligible for a performance claim. The complete contract is specified in [cprofile-runtime-analysis-specification.md](cprofile-runtime-analysis-specification.md).

These local records are not portable evidence. They are excluded from report determinism and may contain host paths. Cache entries use their own strict envelope with a complete cache-key digest, payload digest, and base64-encoded immutable bytes. Phase 3 fingerprint payloads additionally validate source SHA-256 and strict typed records; their keys bind analyzer version, Python version, and relevant configuration. Corrupt, unsupported, or mismatched cache entries are invalidated and recomputed, never accepted as observations.

Until the first release, a report-contract change replaces the draft model and goldens directly. Phase 4J language fields follow this rule. Strictness, deterministic round-trip, unsupported-identifier, language-consistency, and dangling-reference tests remain required; backward-compatible loading and migrations do not.

## Actionable-refactoring schema

The actionable-refactoring work described in [current scope and roadmap](roadmap.md) updates the single unreleased report contract directly. It introduces no compatibility loader or parallel schema generation.

The report contains strict frozen records for adapter capability declarations and independently validated language/section assembly states; stable refactor candidates and report-bound observations; transparent abstraction-cost components and derivations; owner alternatives and abstraction warnings; behavioral events, partial-order edges, invariants, and expanded differences; boundary classes and serialized-shape relationships; Python/JavaScript endpoints, consumers, payload variants, and mismatches; and candidate-specific test requirements. Stable candidate identity excludes proposed ownership/strategy, report hash, source hash, parser version, threshold, rank, and maintainer decision. Report-contained observations bind run, target, static-analysis, source, configuration, parser, evidence, cost, and gate identities without embedding the final report SHA-256; saved projections and ledger entries bind the canonical report SHA-256 externally.

Maintainer decisions use a separate local `code-analysis-decision-ledger` schema rather than being embedded in the canonical analysis report. Each strict record contains the stable candidate ID, optional proposal ID, bounded decision and reason category, concise reason, source-report and candidate-observation identities, strategy/evidence/dependency signature, and optional supersession identity. Local timestamps and paths remain outside portable report identity. Ledger reconciliation and worklist projections operate from saved artifacts without rescanning source and never imply permission to edit code.

Cost values are exact syntax-derived values, bounded estimates, or unresolved values with derivation, confidence, completeness, and limitations. Unknown values cannot serialize as zero. Behavioral ordering retains only statically proven relationships and explicit unresolved regions. Capability declarations prevent the core from manufacturing facts unsupported by an adapter. Final report validation remains strict even when a failed language or section contribution is excluded and represented through diagnostics and partial completeness.

`code-analysis-regression-report@1.0.0` is a separate saved-report-only boundary for domain regressions. It records duplication, ownership, internal-contract, physical/nonblank module growth, candidate readiness/reconsideration, import-edge, SCC, and cycle changes with explicit eligible/retained/omitted counts.

`code-analysis-semantic-nomination-report@1.0.0` is a separate local-provider result. It binds the canonical source-report hash, local model and configuration hashes, vector dimension, provider version, discoverable license-file identities and hash, aggregate supported/rejected/omitted counts, and at most 25 rejected nomination examples. It never persists the model path or promotes a refactor candidate by embedding similarity alone.
## Profile caller representation and availability

`ProfileReport.producer` is a bounded `unknown`, `cprofile`, or `profile` identity. Bare pstats imports use `unknown`, not an inference from one edge. `RuntimeCallEdge.caller_representation` distinguishes `integer-count` from `cprofile-tuple`. Integer edges require null `primitive_calls`, `total_seconds`, and `cumulative_seconds`; timed tuples require all three values. `total_calls` is always an exact nonnegative strict integer, and available primitive counts cannot exceed total counts. The current unreleased schema is updated in place.

External `CollectionMetadata.producer_bindings` and persisted `ProfileReport.producer_bindings` contain strict `{profile_sha256, producer, evidence: "declared"}` records. Declared producers must be `profile` or `cprofile`; hashes are lowercase SHA-256, unique and sorted. Ingestion rejects any binding not matching an input artifact before worker execution, and retains its existing post-normalization input stability check. Persisted bindings must reference profile artifacts and agree with the aggregate producer. A fully bound uniform input set supplies that producer; mixed producers or an undeclared input leave the aggregate unknown while retaining per-file declarations. No declaration is independently authenticated, and source/process/workload completeness is not promoted. Existing metadata without this optional field retains unknown producer identity. See the [CLI example](cli.md) for the supported external metadata shape.

Runtime comparisons expose `profiler_producer` and `caller_edge_timings` compatibility decisions. Frame deltas remain separate from edge metrics; no edge timing is manufactured from frame cumulative time. Caller tables and Markdown expose representation and primitive-count availability, and graph legends distinguish frame timings from count-weighted edges. Raw pstats producer identity remains unresolved without independent capture evidence.
